# local-storage Specification

## Purpose
Локальное хранение данных пользователя: проектов, людей клиента, звонков, карточек задач, вопросов, транскриптов и настроек. Данные переживают перезапуск, а схема без потерь обновляется между версиями приложения.

## Requirements

### Requirement: Локальная база данных
Приложение SHALL хранить данные в одной SQLite-базе в папке данных приложения текущего пользователя ОС. Данные MUST NOT отправляться за пределы машины этой возможностью.

#### Scenario: Данные переживают перезапуск
- **WHEN** пользователь создаёт проект, закрывает приложение и запускает его снова
- **THEN** проект есть в списке с теми же названием и описанием

#### Scenario: Первый запуск
- **WHEN** базы ещё нет
- **THEN** приложение создаёт её с актуальной схемой и пустыми данными

### Requirement: Версионированные миграции
Схема SHALL меняться только упорядоченными миграциями. Номер версии схемы хранится в самой базе. При старте приложение SHALL применить недостающие миграции до первой команды с данными. Если база новее приложения или миграция не прошла, приложение MUST NOT менять данные и SHALL показать ошибку.

#### Scenario: Обновление приложения
- **WHEN** приложение новой версии запускается на базе старой версии
- **THEN** недостающие миграции применяются по порядку, существующие данные сохраняются

#### Scenario: База от более новой версии
- **WHEN** версия схемы в базе больше, чем известно приложению
- **THEN** приложение не пишет в базу и сообщает, что нужно обновить приложение

#### Scenario: Сбой миграции
- **WHEN** миграция завершается ошибкой
- **THEN** изменения этой миграции откатываются, база остаётся на прежней версии

### Requirement: Модель данных
Хранилище SHALL поддерживать связи:
- проект → люди клиента;
- проект → звонки;
- звонок → участники (люди клиента);
- звонок → записи звука (у записи файлы каналов «Я» и «Остальные»). Хранилище SHALL допускать запись, ещё не привязанную к звонку;
- запись → сегменты транскрипта с каналом «Я» или «Остальные» и проходом: живой (во время записи) или уточнённый (после неё). Сегмент SHALL также знать звонок записи, когда запись привязана к звонку;
- запись → темы → карточки задач → вопросы. Тема, карточка и вопрос SHALL также знать звонок записи, когда запись привязана к звонку;
- запись → вызовы агента (время, длительность, токены, результат).

Настройки хранятся отдельно. Удаление проекта SHALL удалять всё, что к нему относится. Удаление звонка SHALL удалять его записи вместе с файлами. Удаление записи SHALL удалять её сегменты транскрипта, темы, карточки, вопросы и вызовы агента. Файлы записи, которой больше нет в базе, MUST быть удалены не позже следующего запуска приложения.

Чтение транскрипта записи SHALL возвращать уточнённый проход, если он есть. Иначе SHALL возвращаться живой проход.

#### Scenario: Удаление проекта
- **WHEN** пользователь удаляет проект
- **THEN** удаляются его люди, звонки, темы, карточки, вопросы, транскрипты и записи звука с файлами, а данные других проектов не меняются

#### Scenario: Транскрипт по каналам
- **WHEN** в запись добавлены сегменты обоих каналов
- **THEN** сегменты читаются в порядке времени, у каждого известен канал

#### Scenario: Уточнённый проход заменяет живой
- **WHEN** у записи есть живые сегменты, и второй проход сохранил уточнённые
- **THEN** чтение транскрипта записи возвращает только уточнённые сегменты

#### Scenario: Человек — участник нескольких звонков
- **WHEN** человек клиента добавлен участником в два звонка проекта
- **THEN** оба звонка показывают его среди участников, а его профиль хранится один раз

#### Scenario: Запись без звонка
- **WHEN** запись сделана до того, как появился звонок в базе
- **THEN** запись, её транскрипт, темы и вопросы хранятся без звонка, а удаление проектов и звонков их не трогает

#### Scenario: Вопросы записи
- **WHEN** во время записи агент создал две темы и пять вопросов, а пользователь удалил запись
- **THEN** темы, карточки, вопросы и вызовы агента этой записи удалены

### Requirement: Поля вопроса
У вопроса SHALL храниться: текст, пояснение, поле карточки, тип пробела (пусто / допущение / противоречие), приоритет, основание (ID сегментов или пунктов проекта и цитата) и состояние: открыт, отвечен, скрыт или задан, а также признак «закреплён».

#### Scenario: Вопрос переживает перезапуск
- **WHEN** агент создал вопрос по противоречию, менеджер его закрепил, а приложение перезапустили
- **THEN** вопрос читается с тем же типом пробела, основанием, приоритетом, состоянием и признаком «закреплён»

### Requirement: Идентификаторы и метки времени
У каждой записи SHALL быть id, выданный бэкендом при создании: UUID v7, глобально уникальный и упорядоченный по времени. Также SHALL быть метки времени создания и последнего изменения в UTC. Фронтенд MUST NOT формировать id сам, в том числе из названий.

#### Scenario: Два проекта с одинаковым названием
- **WHEN** пользователь создаёт два проекта «Телемедиа»
- **THEN** у них разные id, оба открываются по своей ссылке

#### Scenario: Метка изменения
- **WHEN** пользователь меняет описание проекта
- **THEN** метка изменения обновляется, метка создания остаётся прежней

### Requirement: Команды чтения и изменения данных
Бэкенд SHALL предоставлять команды создания, чтения (списком и по id), изменения и удаления для проектов, людей клиента, звонков и их участников, тем, карточек задач и вопросов. Для сегментов транскрипта — только чтение: по записи и по звонку. Сегменты пишет только бэкенд, распознавая записи. Для настроек — чтение и изменение. Входные данные SHALL проверяться. Ошибки SHALL возвращаться с типом («не найдено», «неверные данные», «ошибка хранилища») и текстом.

#### Scenario: Запрос несуществующей записи
- **WHEN** фронтенд запрашивает проект по id, которого нет
- **THEN** команда возвращает ошибку «не найдено», а не пустой объект

#### Scenario: Неверные данные
- **WHEN** фронтенд создаёт проект с пустым названием
- **THEN** команда возвращает ошибку «неверные данные», запись не создаётся

#### Scenario: Ссылка на чужую запись
- **WHEN** фронтенд добавляет в звонок участника из другого проекта
- **THEN** команда возвращает ошибку «неверные данные»

#### Scenario: Транскрипт записи
- **WHEN** фронтенд читает транскрипт записи, которой нет
- **THEN** команда возвращает ошибку «не найдено»

### Requirement: События изменения данных
После каждого успешного изменения бэкенд SHALL отправить событие во все окна приложения. Событие содержит тип сущности, id записи, id проекта (если есть) и вид изменения: создана, изменена или удалена. При ошибке изменения событие MUST NOT отправляться.

#### Scenario: Изменение в одном окне видно в другом
- **WHEN** пользователь переименовывает проект в главном окне при открытом виджете старта
- **THEN** виджет показывает новое название без перезапуска

#### Scenario: Неуспешное изменение
- **WHEN** команда изменения вернула ошибку
- **THEN** окна не получают события об этой записи

### Requirement: Отзывчивость при работе с базой
Операции с базой MUST NOT блокировать интерфейс и обработку других команд, не связанных с базой.

#### Scenario: Долгая запись
- **WHEN** выполняется большая запись в базу, например пакет сегментов транскрипта
- **THEN** окна продолжают отвечать на ввод, а перетаскивание окон не подвисает
