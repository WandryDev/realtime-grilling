# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/`.

Что уже есть:

- **Хранилище.**
  - `projects` (`name`, `description`, `brief` JSON) и `people` (`name`, `role`, `profile` JSON) с CRUD-командами и событиями `DataChanged`.
  - Сервисы `ProjectsData` / `PeopleData` с `layerTauri` и `layerMock`.
  - Сторы `src/data/projects.ts` / `people.ts` (`app-shell-and-storage`).
- **`ProjectsBackend`** (`src/features/projects/backend.ts`) существует только как `layerMock`: `buildBrief` (поток этапов 1…5), `refreshBrief`, `exportMarkdown`.
- **Экраны** берут бриф, источники, звонки и предложения из `src/features/projects/mock.ts` через `project-data.ts`.
  - Форма брифа в макете: `product`, `stack[]`, `modules[]`, `glossary[{ term, definition }]`, `keyDocuments[]`.
  - Шаги мастера: `name → sources → people → notes → building → ready`.
- **Кто уже читает бриф.**
  - Быстрый контур (`agent/fast_loop/assembly.rs`) раскладывает бриф на пункты `B1…` и пропускает `keyDocuments*`.
  - Глоссарий распознавания (`speech/glossary.rs`) берёт `glossary[].term` и `stack[]`.
- **Агент.** `agent::claude_cli::ClaudeCodeCli` даёт вызов с файлом промпта, схемой и отменой. В быстром контуре стоит глобальный семафор «один вызов».
- **Плагинов выбора файлов нет.** Есть `opener` и `os`.

## Goals / Non-Goals

**Goals:**

- Форма брифа совместима с тем, что уже читают быстрый контур и распознавание. Их код не меняется.
- Источник — это абстракция. Сейчас есть только `file`, интеграции добавят свои виды без изменения брифа.
- Логика без агента проверяется в `cargo test`:
  - извлечение текста на фикстурах md / txt (UTF-8 и 1251) / docx / pdf, включая скан;
  - лимиты;
  - отпечаток данных;
  - устаревание;
  - проверка ссылок брифа.

  Сборка проверяется с поддельным CLI.

**Non-Goals:**

- OCR, `.doc`, `.rtf`, `.xlsx`.
- Синхронизация интеграций.
- Правка брифа руками: бриф только собирается, правятся заметки и источники.
- Звонки и предложения на странице проекта (задачи 9–10).

## Decisions

### Источники

**1. Таблица `project_sources` и копии в данных приложения.**

- Поля таблицы:
  - `id`, `project_id` (CASCADE), `kind` (`file`), `name`, `extension`, `size`, `sha256`, `stored_path`;
  - `text`, `text_chars`, `truncated`;
  - `status` (`ready`, `no_text`, `failed`), `error`;
  - `created_at`, `updated_at`.
- Копия файла лежит в `app_data/projects/<projectId>/sources/<sourceId>.<ext>`.
- Дубль определяется по `(project_id, sha256)` с UNIQUE: повторное добавление возвращает существующий источник.
- Удаление источника удаляет файл после коммита.
- Каскадное удаление проекта удаляет папку проекта.
- Сироты (папки без проекта, файлы без строки) чистятся при запуске, как файлы записей.
- Альтернатива — хранить путь к оригиналу. Отклонена: файл переместят, и бриф перестанет собираться.

**2. Текст извлекается в Rust при добавлении.**

| Формат | Как извлекается |
|---|---|
| `.md`, `.txt` | UTF-8, а при невалидном UTF-8 — Windows-1251 (`encoding_rs`) |
| `.docx` | `zip` + `quick-xml`: абзацы `w:p`, текст `w:t`, табуляции и переносы |
| `.pdf` | `pdf-extract`; меньше 20 непробельных символов на страницу — `no_text` («похоже на скан») |

- Текст одного источника ограничен 200 тыс. символов; при обрезке ставится `truncated`.
- Размер файла — до 20 МБ.
- Извлечение идёт в `spawn_blocking`.
- Альтернатива — отдать файлы CLI с инструментом Read, он умеет PDF. Отклонена:
  - инструменты делают вызов непредсказуемым по времени и цене;
  - `.docx` CLI не читает;
  - отпечаток для устаревания нужен по тексту, который видел агент.

**3. Добавление.**

- Выбор файлов идёт через `tauri-plugin-dialog`.
- Перетаскивание — через событие webview `DragDrop` (пути файлов) в окнах `main`.
- Команда `project_sources_add(projectId, paths[])` возвращает результат по каждому файлу: добавлен, дубль или отказ с причиной.

### Бриф

**4. Сборка — отдельный вызов агента.**

- Используется тот же `ClaudeCodeCli`, но со своим промптом и схемой:
  - `--json-schema brief.schema.json`;
  - промпт-файл с правилами брифа на русском: факты только из материалов, без домыслов, глоссарий — термины проекта, ключевые документы — только из списка источников;
  - stdin: описание, заметки, люди, источники с ID `F1…Fn`, именами и текстом.
- Таймаут — 5 минут.
- Модель `claude-sonnet-5-5`, `effort` — `medium`. Бриф собирается редко, качество важнее скорости.
- Сборка брифа не занимает семафор быстрого контура: это отдельный процесс, и обновление перед звонком не должно задерживать вопросы.
- На один проект идёт одна сборка. Повторный запрос во время сборки возвращает текущую.

**5. Схема и хранение брифа.**

- Бриф — JSON `{ product, stack[], modules[{ name, description }], glossary[{ term, definition }], keyDocuments[{ sourceId, title, why }] }`. Ключи `glossary` и `stack` совпадают с теми, что читают распознавание и быстрый контур.
- `keyDocuments` с `sourceId`, которого нет среди источников, отбрасываются при сохранении.
- Колонки `projects`:
  - `brief` (JSON);
  - `brief_built_at`;
  - `brief_inputs` — отпечаток SHA-256;
  - `brief_truncated`;
  - `notes` (TEXT).
- Прежний бриф заменяется только успешным результатом.

**6. Этапы.**

- Событие `BriefProgress { projectId, stage, state }`:
  - stage 1 — чтение источников, отпечаток;
  - stage 2 — запуск агента;
  - stage 3 — агент читает (первый `content_block_delta`);
  - stage 4 — агент пишет (первый `input_json_delta` / `StructuredOutput`);
  - stage 5 — проверка и сохранение.
- `state`: `running | done | failed { message } | cancelled`.
- Это укладывается в существующие `BRIEF_BUILD_STAGES = 5` и прогресс мастера.
- Отмена — команда `brief_cancel(projectId)`: убивает дерево процессов.
- Для этапов 3–4 адаптеру CLI нужен колбэк «первая дельта». Добавляется необязательным полем запроса, быстрый контур не затронут.

**7. Отпечаток и устаревание.**

- `brief_inputs = sha256` от канонического JSON:
  - описание;
  - заметки;
  - люди проекта, отсортированные по id: имя, роль, профиль;
  - `sha256` источников со статусом `ready`, отсортированные.
- Название проекта в отпечаток не входит: переименование не делает бриф устаревшим.
- `outdated = brief != null && brief_inputs != current_inputs`.
- Состояние брифа считается при чтении проекта: `briefState: none | fresh | outdated | building`.
- После изменения людей и источников проекта приходит `DataChanged` проекта, и стор перечитывает его с новым `briefState`.
- Альтернатива — счётчик изменений. Отклонена: правка туда-обратно вернула бы «свежий» бриф только при отпечатке.

**8. Обновление перед звонком.**

- Rust показывает виджет старта (`mic-activity`) и знает его проект: последний проект или выбранный в виджете.
- Команда `brief_prepare(projectId)`. Её вызывает виджет при показе и при смене проекта. Если бриф `outdated` или `none` при непустых материалах, агент готов и сборка не идёт, она запускает сборку в фоне.
- Виджет показывает строку «Обновляю бриф…» из `BriefProgress`.
- Старт записи не ждёт: префикс быстрого контура читает `projects.brief` на момент старта.

**9. Экспорт.**

- `brief_export(projectId, folder)` пишет `<Проект> — бриф.md`: разделы продукт, стек, модули, глоссарий, ключевые документы.
- Папка выбирается через `tauri-plugin-dialog`.
- Имя файла очищается от символов, запрещённых в Windows и macOS.
- Экспорт звонков остаётся мок-кнопкой с пометкой «появится позже».

### Люди и экраны

**10. Профиль.**

- `profile` JSON сохраняет текущую форму фронтенда: `howToAsk`, `askStyle`, `tech`, `project`, `portrait`, `notes`, `initials`.
- Уровни необязательны: `null` показывается как «не указано».
- В Rust профиль валидируется мягко: известные поля проверяются по типу, неизвестные сохраняются.
- Быстрый контур уже передаёт профили.

**11. Фронтенд.**

- `ProjectsBackend.layerTauri`:
  - `buildBrief` — `Stream` из `BriefProgress` после `brief_build`;
  - `refreshBrief`;
  - `exportMarkdown("brief")`;
  - `prepareBrief`.
- Новый сервис `ProjectSourcesData` с `layerTauri` и `layerMock`.
- `project-data.ts` перестаёт подмешивать демо-бриф, источники и звонки к настоящим проектам:
  - демо остаётся только в mock-слое у сид-проектов;
  - разделы звонков и предложений у настоящих проектов показывают пустое состояние;
  - открытые вопросы и последняя запись на главной считаются по `questions` / `recordings` проекта новой командой `projects_overview`.
- Шаг «Источники» мастера: блок «Документы с компьютера» (выбор и перетаскивание, список с состояниями) из компонентов дизайн-системы. Outline, GitHub и ClickUp — строки с пометкой «скоро», выключены.
- Шаг «Заметки» сохраняет `notes`.
- «Собрать бриф» запускает `brief_build`.
- В браузере и тестах всё остаётся на `layerMock` с демо-данными.

## Risks / Trade-offs

- **[`pdf-extract` падает или зависает на кривых PDF.]** → Извлечение идёт в `spawn_blocking` с таймаутом 30 с и `catch_unwind`. Ошибка даёт статус `failed` с текстом, приложение работает.
- **[Сборка брифа тратит заметную часть лимита: длинный вход, effort medium.]** → Сборка запускается по действию менеджера или перед звонком только при устаревшем брифе. В `agent_calls` сборка не пишется (там вызовы записи), стоимость логируется.
- **[Агент выдумывает факты в брифе.]** → Промпт требует факты только из материалов, а ссылки ключевых документов проверяются. Пункты брифа без источника допустимы, если они из заметок. Полнота проверяется в задаче «Качество вопросов».
- **[Перетаскивание на Windows и macOS ведёт себя по-разному.]** → Используется событие Tauri `DragDrop`, оно даёт пути на обеих ОС. Кнопка выбора файлов есть всегда.
- **[Большие материалы.]** → Пропорциональное сокращение и пометка в брифе. Разбиение на несколько вызовов — когда появятся реальные объёмы.

## Migration Plan

- Миграция 0005 добавляет колонки `projects` и таблицу `project_sources`. У существующих проектов бриф `null`, заметки пустые.
- Копия базы перед миграцией делается как обычно.
- Changeset `minor`.

## Open Questions

- Лимит текста на сборку. Стартовое значение — ~300 тыс. символов (~100 тыс. токенов); уточнится по реальным проектам и цене.
- Нужна ли правка брифа руками. Пока нет, заметки покрывают уточнения.
