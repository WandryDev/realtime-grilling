# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/`.

**Цифры спайка** (`docs/spikes/agent.md`). Claude Code CLI с Sonnet в минимальном режиме:

- задержка p50 12.8 с, p95 17.2 с;
- 70 из 70 ответов по схеме;
- ≈ $0.04 за вызов в API-эквиваленте.

Что известно о самом CLI:

- **Haiku через CLI медленнее Sonnet**: thinking не выключается.
- **Конфиг пользователя добавляет ~7 с и ~$0.10 на вызов.**
- **`--json-schema`** — это инструмент `StructuredOutput`. Без фразы «передай патч вызовом StructuredOutput» CLI делает второй запрос (+10 с).
- **`--bare` с подпиской не работает.**
- **`--system-prompt` кешируется лучше**, чем `--append-system-prompt`.

**Что уже есть в коде:**

- **`src-tauri/src/agent/`** (задача 3):
  - поиск CLI, статус без вызова модели, установка, вход;
  - `process.rs` запускает процесс с деревом и убивает его по таймауту, на Windows — через Job;
  - `fake_cli_tests.rs` — образец тестов с поддельным CLI.
- **Живой проход STT** (задача 5): `SpeechHost::emit(TranscriptEvent::Phrase)` после записи сегмента в базу. Также `live_finished(recording_id)`.
- **Запись** знает проект и участников (`recordings.project_id`, `participant_ids`). Глоссарий уже собирается в `speech/glossary.rs`.
- **Таблицы `topics`, `task_cards`, `questions`** привязаны к `calls` (`call_id NOT NULL`). Звонков в базе пока нет (задача 9), поэтому таблицы пусты.
- **Фронтенд.**
  - `CallBackend` подаёт ленту из сценария (`feed-script.ts`); в Tauri уже идёт настоящая расшифровка.
  - Быстрые действия (`asked` / `pin` / `hide`, «Вернуть», «Открепить») живут только в редьюсере `live-call.ts`.
  - Настройки: `questionFrequency` (`rare` / `normal` / `often`), `questionCount` (`1` / `3` / `5`), `finalCheck` (минуты «за сколько до конца»).

## Goals / Non-Goals

**Goals:**

- Логика без модели проверяется в `cargo test`:
  - планировщик (с `tokio::time::pause`);
  - сборка вызова и побайтная стабильность префикса;
  - разбор `stream-json`;
  - проверка оснований, дедупликация и лимиты;
  - применение патча и видимый список.

  Сквозной тест — с поддельным CLI.
- Одно состояние вопросов для всех окон, его считает бэкенд.
- Адаптер CLI — единственное место, которое знает про Claude Code.

**Non-Goals:**

- Эмбеддинги, прямой API, медленный контур, интеграции.
- Оценка полезности вопросов (задача «Качество вопросов»).
- Финальная проверка по таймеру «за N минут до конца»: время конца звонка неизвестно, пока нет календаря.

## Decisions

### Агент и вызов

**1. `trait Agent` + `ClaudeCodeCli`.**

```rust
async fn run(&self, request: AgentRequest, cancel: oneshot::Receiver<()>)
    -> Result<AgentReply, AgentError>
```

- `AgentReply`: патч (`serde_json::Value` до проверки) и `Usage` (длительность, токены, кеш, стоимость, доля лимита, время сброса).
- `AgentError`: `Timeout`, `NotLoggedIn`, `RateLimited { resets_at }`, `InvalidOutput`, `Process(String)`.
- Адаптер запускает CLI с флагами из спайка:
  - `-p --model claude-sonnet-5-5 --effort low --setting-sources "" --strict-mcp-config --tools "" --no-session-persistence --disable-slash-commands`;
  - `--system-prompt <prefix> --json-schema <schema> --output-format stream-json --verbose --include-partial-messages`;
  - env `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`;
  - cwd — `app_data_dir()/agent`;
  - переменная часть идёт в stdin.
- Модель задана полным именем и вынесена в константу.
- Разбор `stream-json` построчный и терпим к неизвестным событиям. Берутся `result.structured_output`, `result.usage`, `total_cost_usd` и `rate_limit_event`.
- `NotLoggedIn` и `RateLimited` распознаются по `result.is_error` / `subtype` и тексту ошибки. Образцы строк лежат в фикстурах тестов.
- Альтернатива — держать одну сессию CLI на звонок. Отклонена концептом: контекст растёт, а сжатие неконтролируемо.

**2. Планировщик: один на запись.**

- Это tokio-задача, она стартует вместе с живым проходом записи. Хост приложения пересылает ей `TranscriptPhrase` с `pass = live`. Остановка — по `live_finished`.
- Состояние задачи:
  - `last_start`;
  - `new_since_last` — были ли фразы после последнего вызова;
  - `in_flight`;
  - `retry_at`.
- **Правило старта.** Вызов стартует, когда одновременно:
  - пришла фраза канала `others`;
  - вызов не идёт;
  - `now - last_start ≥ interval`, где интервал: `rare` → 45 с, `normal` → 20 с, `often` → 10 с;
  - есть новые фразы.
- Пауза в речи уже заложена в VAD: фраза заканчивается паузой. Отдельного детектора паузы нет.
- **После ошибки** `retry_at = now + 30 с`. Повтор срабатывает сам по таймеру. Команда `agent_retry(recording_id)` повторяет сразу.
- **`NotLoggedIn` и `RateLimited`** останавливают вызовы до конца записи. После `RateLimited` повтор разрешается не раньше `resets_at`.
- Настройка интервала читается при каждом решении, поэтому её изменение действует сразу.

**3. Сборка вызова.**

- **Стабильный префикс** собирается один раз при старте планировщика и хранится в нём. Поэтому правка проекта во время звонка не ломает кеш, а новые данные попадут в следующий звонок. Префикс содержит:
  - правила: протокол патча, правила качества из концепта, оговорку об ошибках распознавания и о том, что факты берутся только из «Остальных»;
  - проект (`P1` — описание, `B1…Bn` — пункты брифа, если бриф есть);
  - людей с профилями;
  - глоссарий из `speech/glossary.rs`.
- **Переменная часть** (stdin):
  - режим (`обычный` / `финальная проверка`);
  - состояние: темы с ID, текущая тема, её карточка, открытые / скрытые / заданные вопросы с ID;
  - расшифровка за 10 минут строками `[S:<id>] mm:ss Остальные|Я: текст` из живого прохода;
  - в конце — «Передай патч одним вызовом инструмента StructuredOutput».
- Тест проверяет, что два вызова одного планировщика дают побайтно равный префикс.

**4. Патч: схема и типы.**

- Операции (`op`):

  | `op` | Поля |
  |---|---|
  | `topic` | `action: create \| switch`, `topicId?`, `title?` |
  | `card` | `field`, `value`, `evidence[]` |
  | `question` | `title`, `description`, `cardField`, `gapType: empty \| assumption \| contradiction`, `priority: 1–3`, `evidence[]` |
  | `answered` | `questionId`, `evidence[]` |
  | `finalCheck` | — |

- `evidence` — это `{ source: segment | project, id, quote }`.
- JSON Schema лежит файлом `agent/patch.schema.json` и встраивается `include_str!`.
- Serde-типы описаны рядом. Тест прогоняет набор примеров через схему (`jsonschema`, dev-зависимость) и через serde и сверяет результат.
- Противоречие — это вопрос с `gapType = contradiction` и двумя основаниями из разных сегментов.

### Проверка и применение

**5. Проверка основания.**

- **Нормализация:** lower-case, ё→е, без пунктуации, схлопнутые пробелы.
- **Совпадение цитаты.** Цитата из n слов ищется окном из n слов в тексте основания. Слово совпадает, если равно или его сходство по Левенштейну ≥ 0.75. Цитата принята, если совпало ≥ 80% слов. Так проходит одно искажённое слово при ASR-ошибке.
- **ID** должен быть в переданном контексте: в окне расшифровки этого вызова или в пунктах проекта.
- **Вопрос** должен ссылаться на `cardField` карточки текущей темы. Новое поле карточки можно создать операцией `card` в том же патче, раньше вопроса.
- **Журнал.** Отброшенная операция пишется с причиной в `agent_calls.rejected` (JSON) и в лог.
- Отклонено: LLM-критик (+2–5 с, концепт).

**6. Повторы и лимиты.**

- `trait QuestionSimilarity` с реализацией `TrigramSimilarity`: коэффициент Дайса по символьным триграммам нормализованного текста, порог 0.6. Пороги подбираются тестами на парах вопросов с разными окончаниями и порядком слов.
- Новый вопрос сравнивается с вопросами записи в состояниях `open`, `answered`, `hidden` и `asked`.
- Новые вопросы одного патча сортируются по `priority`, принимаются первые два.
- Эмбеддинги можно подключить второй реализацией трейта.

**7. Видимый список считает бэкенд.**

- У вопроса есть `shown_at` — момент, когда он стал видимым.
- После каждого изменения бэкенд пересчитывает видимые вопросы текущей темы:
  - закреплённые;
  - уже видимые открытые, в прежнем порядке `shown_at`;
  - свободные места до `questionCount` заполняются ожидающими по `priority desc, created_at asc`.
- Ушедший (отвеченный, скрытый, заданный) освобождает место.
- Так все окна видят одно и то же, и порядок не скачет (`call-questions`: «Стабильный список»).
- Альтернатива — считать во фронтенде. Отклонена: окна, открытые в разное время, получили бы разный порядок.

**8. Финальная проверка.**

- Операция `finalCheck` ставит у записи `final_check_at` (колонка в `recordings`).
- Окна показывают открытые вопросы всех тем: топ `questionCount` по `priority desc, created_at asc`.
- Следующие вызовы идут в режиме «финальная проверка». Агент может отмечать отвеченные, новых тем не создаёт: это правило промпта, а код отбрасывает `topic create`.
- Выход из финальной проверки — чисто экранное состояние окна, бэкенд не меняется.
- Настройка `finalCheck` (минуты) пока не участвует. Об этом — в Open Questions.

### Хранение, команды, события

**9. Миграция 0004.**

- Пересоздаются `topics`, `task_cards`, `questions`, как это делала 0003 для расшифровки. Строк в них нет, потому что звонки не создавались. Миграция логирует, сколько строк удалено.
- Во всех трёх таблицах: `recording_id NOT NULL` → `recordings ON DELETE CASCADE`, `call_id` nullable → `calls ON DELETE CASCADE`.
- `questions` дополнительно получает:
  - `description`, `card_field`, `gap_type`, `priority`, `evidence` (JSON), `answer_evidence` (JSON);
  - `status CHECK (open, answered, hidden, asked)`, `pinned`, `shown_at`.
- `recordings` получает `final_check_at` и `current_topic_id`.
- Новая таблица `agent_calls`:
  - `id`, `recording_id` (CASCADE), `started_at`, `duration_ms`;
  - `outcome`: `ok`, `empty`, `invalid`, `error`, `timeout`, `rate_limited`, `not_logged_in`;
  - токены, `cache_read`, `cache_write`, `cost_usd`, `utilization`;
  - `rejected` (JSON), `error`.
- Патч применяется одной транзакцией.

**10. Команды и события.**

- **Команды:**
  - `call_state_get(recordingId)` → `{ topics, currentTopicId, cards, questions (с visible/rank), finalCheck, agent }` — одно чтение всего состояния звонка;
  - `questions_act(id, action: pin | unpin | hide | asked | restore)`;
  - `agent_retry(recordingId)`.
- **Права.** Все три команды доступны `main` и `floating`. Старые `topics_*` / `task_cards_*` / `questions_*` CRUD по `call_id` удаляются: ими никто не пользуется, а модель изменилась.
- **События:**
  - `CallStateChanged { recordingId }` — после применённого патча или быстрого действия; окна перечитывают состояние, как сторы по `DataChanged`, с защитой от устаревших ответов;
  - `AgentStatus { recordingId, state, utilization? }`, где `state` — `idle | thinking | error { message, retryAt } | needsLogin | rateLimited { resetsAt? }`.

### Фронтенд

**11. Окно звонка и оверлей.**

- `CallBackend.layerTauri` читает `call_state_get` по `CallStateChanged` и слушает `AgentStatus`.
- Адаптер `src/features/call/agent-state.ts` переводит данные в `TopicData` / `OpenQuestionData` / `HistoryEntry` / финальную проверку. Подписи ленты («отвечено», «противоречие» со ссылкой на время) строятся из `evidence` вопросов.
- Быстрые действия вызывают `questions_act`. Редьюсер в Tauri больше не держит `stash`: история и «Вернуть» берутся из состояния бэкенда.
- Баннеры: `AgentStatus.error` → «Сам попробую через N с» + «Повторить» (`agent_retry`); `needsLogin` → ссылка на «Настройки → Агент»; `rateLimited` → время сброса.
- В браузере и тестах остаётся сценарий `feed-script.ts` через `layerMock`, с тем же интерфейсом сервиса.

## Risks / Trade-offs

- **[Формат `stream-json` CLI меняется между версиями.]** → Терпимый разбор: неизвестные события пропускаются. Фикстуры реальных строк лежат в тестах, минимальная версия CLI зафиксирована в `agent-setup`. Ошибка разбора даёт `InvalidOutput`, а не панику.
- **[Лимит подписки при 90–180 вызовах в час.]** → Доля лимита видна в окне, при `RateLimited` вызовы останавливаются, а `agent_calls` даёт цифры для решения о прямом API.
- **[Триграммы пропускают перефразировки.]** → Агент и так видит открытые, скрытые и заданные вопросы с ID. Если прогон звонков покажет пропуски, второй реализацией подключаются эмбеддинги.
- **[Нечёткое совпадение цитаты отсечёт честный вопрос.]** → Пороги покрыты тестами на реальных ASR-ошибках из синтетики спайка, отказы видны в журнале. Пороги — константы, их подстроит задача «Качество вопросов».
- **[Изменение проекта во время звонка не попадает в префикс.]** → Осознанно, ради кеша. В следующем звонке будет новая версия.
- **[Миграция 0004 удаляет строки старых таблиц.]** → Их нет: звонки не создавались. Миграция логирует количество.

## Migration Plan

- Миграция 0004 применяется при запуске. Резервная копия перед миграцией уже есть (`app-shell-and-storage`).
- Откат: старая версия приложения откажется работать с базой новее себя, копию `grill.db.bak-v3` можно вернуть.
- Changeset `minor`.

## Open Questions

- **Настройка «Финальная проверка: за N минут до конца».** Время конца звонка станет известно с календарём (отложен). До этого настройку можно скрыть или переименовать. Это решение по UI, на механизм не влияет.
- **Пороги совпадения цитаты (0.75 / 80%) и повторов (0.6)** уточнятся на записанных звонках в задаче «Качество вопросов».
