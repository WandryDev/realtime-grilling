# Design

## Context

Что есть сейчас (подробная карта экранов собрана перед предложением):

- **Демо вместо звонка.** Все страницы после звонка (`src/features/post-call/pages/*`) показывают демо «Телемедиа» из `post-call/mock.ts`. Настоящие у звонка только строка в базе (дата, длительность, участники, проект) и решения в JSON `calls.summary`. Ключи этих решений — глобальные id из мока (`"operators"`, `"calls"`), одинаковые для всех звонков.
- **Сборка итогов.** Её ведёт webview (`post-call/api.ts collectSummary` → `PostCallBackend.buildSummary`). Настоящий только шаг 0: второй проход последней записи с отступлением на живую расшифровку через 60 с тишины. Шаги 1–3 — таймеры. В конце `closeCall`. «Собираю итоги» в окне звонка — свой таймер (`call/backend.ts collectSummary`).
- **Данные в базе** (по записям, не по звонку):
  - темы, `task_cards` (одно значение на линзу, основания, `decision`, `title`);
  - вопросы (`status`, `gap_type`, `card_field`, `evidence`, `answer_evidence`);
  - живая и уточнённая расшифровка (`transcript_for_recording`, `transcript_list(callId)` — фронтенд их не вызывает), бриф, профили, заметки.
- **Основания вопросов и карточек** ссылаются на id живых сегментов. После второго прохода чтение отдаёт уточнённые, и время по такому id фронтенд не найдёт.
- **Аудио.** `recordings/<id>/{me,others}.opus` (Ogg Opus, моно, 16 кГц). Пути не выходят из Rust. Воспроизведения нет. «Удалить запись» ставит `audioDeleted` в JSON, файлы остаются.
- **Для переиспользования:**
  - `ClaudeCodeCli` (`agent/claude_cli.rs`), сборка брифа (`projects/brief/*`): схема в `--json-schema` до ~4 КБ, рамки с nonce, этапы, отмена, один запуск на ключ (`builds.rs`), поддельный CLI в тестах;
  - проверка цитат `fast_loop/evidence.rs`;
  - `CallManager` (`src-tauri/src/call/`) с `call_close`.

## Goals / Non-Goals

**Goals:**

- Бэкенд целиком ведёт сборку итогов, а окна только показывают её этапы и результат.
- Всё, что показывает агент, проходит проверку кодом: ссылки на сегменты, вопросы и людей, совпадение цитат, канал «Остальные» для фактов.
- Принятое предложение меняет данные и отменяется. Непринятое ничего не меняет.
- Экраны сохраняют мок-значения по умолчанию: `/dev` и превью работают как раньше.

**Non-Goals:**

- Изменение внешнего вида экранов: только данные, состояния ошибок и «скоро».
- Индекс полнотекстового поиска (см. решение 11).
- Перенос вопросов в следующий звонок, интеграции, экспорт.

## Decisions

### 1. Модуль `summary/`: сборка ведёт Rust

`src-tauri/src/summary/` с `SummaryBuilds` (одна сборка на звонок, как `BriefBuilds`).

**Когда сборка начинается и останавливается:**

- **Старт.** `CallManager` при переходе в `Finishing` вызывает `SummaryBuilds::start(callId)`.
- **Отмена.** При `resume`, `discard` и удалении звонка `CallManager` отменяет сборку: процесс CLI убивается, ничего не сохраняется.
- **Конец.** По завершении (успех, ошибка агента, отмена пересборки) сборка вызывает `CallManager::close(callId)`. Тот закрывает звонок, если он ещё в `Finishing` этого звонка. Так спецификация «звонок завершён по окончании сборки, успешной или нет» выполняется без окон.

**Команды:**

| Команда | Что делает | Окна |
|---|---|---|
| `summary_get(callId)` | итоги звонка или их отсутствие, состояние сборки | все |
| `summary_build(callId)` | «Собрать итоги» для завершённого звонка | главное |
| `summary_cancel(callId)` | остановить сборку | главное |

Событие `SummaryProgress { callId, stage, state }` (`Running` / `Done` / `Failed{message}` / `Cancelled`) по образцу `BriefProgress`.

**Альтернатива** — оставить сборку в webview. Не подходит: перезагрузка окна теряет сборку, окно должно закрывать звонок, а после сбоя нечего продолжать.

### 2. Этапы

1. **`transcript`.**
   - Ждать второй проход каждой записи звонка: прогресс уже идёт событиями распознавания.
   - Отступление на живую расшифровку, если 60 с нет вестей, проход упал или у записи удалено аудио.
   - В итоги записывается `transcriptPass: refined | live | mixed`.
2. **`summary`** — вызов агента A.
3. **`proposals`** — вызов агента B. Его нет у звонка без проекта.
4. **`saving`** — проверка и сохранение в одной транзакции.

**Перед сохранением сборка ещё раз проверяет флаг отмены под замком базы, как бриф.**

«Собираю итоги» в окне звонка и шаги на странице итогов строятся из `SummaryProgress`. Таймеры `CallBackend.collectSummary` и `PostCallBackend.buildSummary` остаются только в `layerMock`. Описания этапов считаются из данных: «N реплик, M тем».

### 3. Два вызова агента

Модель `claude-sonnet-5-5`, effort `medium`, таймаут 10 мин на вызов. Общий вход с рамками nonce, как `brief/input.rs`:

- **проект:** `P1` — описание, `B1…Bn` — пункты брифа, заметки;
- **люди звонка:** `H1…` с профилями;
- **расшифровка:** строки `[S12] 00:21:08 Клиент|Вы: текст` по всем записям. Время от начала звонка, `S#` — id выбранного прохода;
- **состояние быстрого контура:** темы `T#`, карточки с полями, вопросы `Q#` со статусом, типом пробела и полем.

Лимит входа — `BUDGET_CHARS` брифа. Длинная расшифровка сокращается равномерно с пометкой агенту.

**Ответ A** (схема до 4 КБ):

```json
{
  "title": "",
  "tldr": "",
  "topics": [{
    "ref": "T1 | new",
    "title": "",
    "from": "S#",
    "to": "S#",
    "points": [{ "text": "", "status": "fact|assumption|contradiction", "evidence": [{ "id": "S#", "quote": "" }] }],
    "card": {
      "title": "",
      "fields": [{ "field": "<CardLens>", "facts": [{ "text": "", "status": "confirmed|assumption|contradiction|empty", "evidence": [] }] }]
    }
  }],
  "answered": [{ "ref": "Q#", "evidence": [] }],
  "next": [{ "text": "", "topic": "T#", "field": "<CardLens>", "gap": "empty|assumption|contradiction" }]
}
```

**Ответ B:**

```json
{
  "proposals": [{
    "target": "brief | H#",
    "field": "",
    "after": "",
    "kind": "said|inferred",
    "evidence": []
  }]
}
```

- Поля брифа: `product`, `stack`, `modules`, `glossary`.
- Поля профиля: `role`, `tech` (1–5), `project` (1–5), `howToAsk`, `portrait:<метка>` (четыре метки портрета), `notes`.

**Почему два вызова:**

- одна схема не помещается в лимит командной строки;
- у B другой контекст (бриф и профили важнее расшифровки);
- сбой B не лишает звонок итогов.

### 4. Проверка ответа кодом

**Для A и B:**

- Ссылки `S/T/Q/H/B`, которых не было во входе, отбрасываются.
- Каждая цитата проверяется `evidence::quote_matches` по сегментам выбранного прохода.
- Пункт, факт, ответ на вопрос и предложение `said` требуют основания из «Остальных» или проекта. Противоречие требует двух фраз клиента.
- Факт, у которого цитаты не нашлись, становится «вывод агента» (без цитаты), а не «подтверждено».
- Лимиты: тем ≤ 12, `next` ≤ 5, предложений ≤ 12.

**Только для B:**

- `before` предложения берёт код из текущего брифа или профиля.
- Предложение, равное текущему значению, отбрасывается.
- Для `tech` и `project` — только число от 1 до 5.

**Ответ не по схеме.** Этап `Failed`, прежние итоги не трогаются, звонок закрывается (решение 1).

### 5. Хранение: миграция `0007`

- **`call_summaries`**:
  - ключ `call_id` (FK на `calls`, CASCADE);
  - `state` (`building` / `ready` / `failed`), `error`, `transcript_pass`;
  - `title`, `tldr`;
  - `content` JSON: темы с диапазонами и пунктами, карточки с фактами, `next`;
  - `built_at`, `created_at`, `updated_at`.
- **Основания в `content`** хранят `recordingId`, `segmentId`, `startMs` и цитату. Окнам не нужно искать время по id сегмента.
- **Id карточек.** Код выдаёт UUID v7 при сохранении. Решение менеджера и название хранятся в самой карточке `content`.
- **`call_proposals`**:
  - `id`, `call_id` (CASCADE);
  - `target` (`brief` / `person`), `person_id` (CASCADE);
  - `field`, `before`, `after`, `kind`, `evidence` JSON;
  - `decision` (`pending` / `accepted` / `rejected`), `edited`, `applied` JSON (что записано и прежнее значение);
  - `decided_at`, `created_at`, `updated_at`.
- **`recordings.audio_deleted_at`.**
- **`calls.title`.** Пишется из итогов, если пуст.
- **Пересборка** в одной транзакции заменяет `call_summaries` звонка и предложения `pending`. Принятые и отклонённые остаются.
- **`calls.summary` JSON фронтенда** теряет `proposals`, `tasks` и `audioDeleted`: эти данные теперь в таблицах. Остальное остаётся за фронтендом.
- **Звонок, закрытый `finish_stale` без итогов,** читается как `state: failed`, `error: "interrupted"`.

**Альтернатива** — расширить JSON фронтенда. Не подходит: Rust должен проверять, применять, искать и менять это в транзакциях.

### 6. Сверка вопросов

`answered` из ответа A после проверки цитат меняет `questions.status` с `open` или `asked` на `answered` с `answer_evidence`. Отвеченные и скрытые не трогаются. Это делается в той же транзакции сохранения.

### 7. Карточки

- **После итогов** страница карточек читает карточки из `content`.
- **До итогов или при `failed`** — `task_cards` всех записей звонка: одно значение на линзу, состояние по вопросам этого поля, как в карте экранов.
- **Решения.** Команда `call_card_update(callId, cardId, { decision?, title? })` пишет решение в карточку `content` или в `task_cards.decision` / `title` для карточек быстрого контура.
- **Отправка в трекер.** В Tauri `sendTaskCard` не вызывается, кнопки «скоро».

### 8. Применение предложений

Команды `proposal_decide(id, { decision, edited? })` и `proposal_undo(id)`, главное окно. Изменение данных и решение — в одной транзакции.

**Профиль:**

- `role` — колонка `people.role`;
- остальные поля — `profile` JSON;
- запись по схеме read-modify-write; в `applied` сохраняются прежнее и записанное значения.

**Бриф.** В `projects.notes` дописывается строка `- <дата звонка>: <текст>` в разделе `## Из звонков` (раздел создаётся, если его нет). Лимит `NOTES_MAX_CHARS` проверяется: превышение — `Invalid` с причиной. Заметки и люди входят в отпечаток брифа, поэтому бриф сам становится `outdated`.

**Отмена:**

- если текущее значение равно записанному, возвращается прежнее (для заметок — убирается именно эта строка);
- иначе `Invalid` «Поле изменили после принятия», ничего не меняется.

Шлётся `DataChanged` проекта или человека.

**Страница человека.** Подсказка «изменения из звонка» (`profile.suggestion` из мока) заменяется списком ожидающих `call_proposals` этого человека со ссылкой на ревью.

### 9. Аудио: своя схема

**Отдача файлов.** `register_asynchronous_uri_scheme_protocol("grill-audio")`, адрес `grill-audio://localhost/<recordingId>/<me|others>`; на Windows `http://grill-audio.localhost/…`.

- Rust находит файлы по id и отдаёт байты с поддержкой `Range` (206).
- Если у записи удалено аудио — 404.
- Пути не выходят из Rust.

**Ogg Opus в WKWebView.** Его поддержка — риск, поэтому первая задача — спайк: `canPlayType` и реальное воспроизведение в подписанном бандле. Если WebKit не играет, тот же адрес с `?format=wav` отдаёт WAV.

- WAV Rust декодирует крейтами `opus` и `ogg` во временный кеш (16 кГц, 16 бит, моно, ~115 МБ на час на канал).
- Кеш удаляется при выходе и при удалении аудио.

**Каналы.** Два элемента `<audio>`: «Оба» — оба играют, «Только вы» / «Только клиент» — у второго `muted`. Плеер держит их вместе: ведущий — «Клиент», ведомый подстраивается при расхождении больше 150 мс.

**Волна.** Команда `recording_peaks(recordingId, bars)` декодирует в Rust и кеширует пики.

**Несколько записей.** У звонка из нескольких записей переключатель частей.

**Альтернатива** — asset-протокол с путями. Не подходит: открывает пути и всю папку записей любому окну.

### 10. Удаление аудио

Команда `call_audio_delete(callId)`, главное окно. Для каждой записи звонка:

1. остановить второй проход этой записи, если он идёт;
2. удалить оба файла через `RecordingStore`;
3. записать `audio_deleted_at`;
4. отправить `DataChanged`.

Затем почистить кеш WAV и пиков.

Второй проход, `recover_interrupted` и уборка файлов пропускают записи с `audio_deleted_at`. Живая запись не удаляется: звонок должен быть завершён.

### 11. Расшифровка, вопросы и поиск звонка

**`call_transcript(callId)`** отдаёт записи звонка: `id`, `startedAt`, `endedAt`, `audioDeleted`, проход, длительность, размер файлов и сегменты выбранного прохода.

**`call_questions(callId)`** отдаёт вопросы звонка с моментом основания и ответа (`recordingId`, `startMs`). Rust находит время по id сегмента любого прохода.

**`calls_search(query, projectId?)`** — перебор в Rust:

- нормализация, как в `evidence::normalize` (регистр, «ё»);
- источники: сегменты выбранного прохода, название, TL;DR, пункты, факты карточек;
- до 200 совпадений, фрагмент ± 60 символов, счётчики по проектам.

**Почему без FTS5:** на сотнях звонков перебор быстрый, нет индекса, который надо поддерживать, и нет проблем с кириллицей в `LIKE`. FTS5 со словарём `trigram` доступен в сборке SQLite, если понадобится.

**Время в оконных часах** = `recording.started_at + startMs`. `moment.ts` переходит на настоящие сегменты, без постоянной `12:01`.

### 12. Фронтенд

**Новые сервисы с `layerTauri` и `layerMock`:**

- `SummaryData`: итоги, прогресс, сборка;
- `ProposalsData`: решения и отмена;
- `CallRecordsData`: расшифровка, вопросы, удаление аудио, пики;
- поиск в `CallsData`.

`layerMock` отдаёт нынешнее демо, контракт закреплён в `data-contract.test.ts`.

**Страницы:**

- берут настоящие данные и передают их экранам; мок-значения по умолчанию у экранов остаются для `/dev`;
- «Ответы для ClickUp» и шаг ClickUp не показываются в Tauri;
- кнопки трекера — «скоро».

**История:**

- сортировка по `startedAt`;
- фильтры по `participantIds`;
- готовность из `briefState`, источников и людей;
- название — `calls.title`, иначе первая тема, иначе проект.

## Risks / Trade-offs

- [WKWebView не играет Ogg Opus] → спайк первым. Запасной путь — WAV из Rust, это больше места во временном кеше, только пока открыта страница.
- [Два `<audio>` расходятся] → ведущий элемент и подстройка при расхождении больше 150 мс. На «Только …» играет фактически один канал.
- [Агент выдумывает] → цитаты проверяются кодом, без цитаты факт — «вывод агента», а применяется только принятое менеджером.
- [Сверка вопросов закроет вопрос ложно] → закрытие только с цитатой клиента, прошедшей проверку. Ответ виден в деталях, вопрос можно вернуть.
- [Стоимость: два вызова medium на звонок, вход до 300 тыс. символов] → вызовы раз в звонок, стоимость пишется в лог. Замер — в живом прогоне (`docs/spikes/agent.md`).
- [Длинная сборка держит звонок в «завершается»] → виджет и «Сразу записывать» не работают до конца сборки (до ~20 мин в худшем случае). «Остановить» на странице итогов отменяет сборку и закрывает звонок с `failed`, а итоги собираются кнопкой позже.
- [Отмена принятого после ручной правки] → отмена отказывает с причиной, а не затирает правку.
- [Миграция `0007`] → новые таблицы и колонка, без пересборки таблиц. Копия базы до миграции сохраняется.

## Migration Plan

Миграция `0007` при первом запуске новой версии. Старые звонки получают итоги `failed: interrupted` и кнопку «Собрать итоги»: их расшифровка есть, итоги собираются по запросу. Старые решения из `calls.summary.proposals` / `tasks` (демо-id) не переносятся.
