## Context

Мотивация — в proposal.md. Что важно для подхода:

- **Быстрый контур** (`src-tauri/src/agent/fast_loop/`) устроен так, что прогон в него встраивается без копирования логики:
  - `FastLoop` держит по планировщику на запись;
  - фразы приходят через `FastLoop::phrase`, всё остальное (база, события окнам) идёт через трейт `LoopHost`;
  - агент — трейт-объект, который выдаёт `AgentProvider`;
  - планировщик меряет время `tokio::time::Instant`, поэтому тесты уже идут на остановленных часах с поддельным агентом (`testing.rs`).
- **Метки времени.** Окно расшифровки (10 минут) считается по `end_ms` сегментов, от стенных часов оно не зависит. А время создания вопросов и вызовов в базе берётся из `now_ms()`, то есть со стенных часов.
- **Стабильная часть промпта** (`assembly::build_prefix`): правила, `P1` (описание), `B1…Bn` (пункты брифа без `keyDocuments`), люди, глоссарий. Основание вопроса со `source: project` проверяется по этим пунктам (`SourceText`).
- **Проверка в `validate.rs`.** Для типа пробела `empty` код не требует, чтобы поле было пустым. Для `assumption` и `contradiction` требует, чтобы поле было заполнено. Метка `empty` на экране не показывается, поэтому «не раскрыто» помещается в нынешнее значение без миграции.
- **Бриф** (`projects/brief/`): `Brief` с `deny_unknown_fields`, схема ответа `brief.schema.json`, промпт `prompt.md`, экспорт `export.rs`. Тексты прочитанных источников лежат в `project_sources.text`.
- **Корпус.** Уже есть реальный звонок 05.11 на 75 минут (775 живых сегментов, 271 вызов, 11 вопросов) и шесть коротких звонков 04.11 с искусственным клиентом. Будут аудиозаписи звонков с реальными клиентами, сделанные вне приложения: формат (моно или две дорожки) пока неизвестен. Это разговоры клиентов, в репозиторий их класть нельзя.
- **Распознавание.** Живой проход — это VAD-нарезка (`vad::worker`, `PhraseSink`) и живые задания распознавателя (`speech/live.rs`). Второй проход (`speech/refiner.rs`) заново нарезает два файла Ogg Opus записи и распознаёт с beam search и полным глоссарием. Оба прохода работают с 16 кГц моно на канал.

## Goals / Non-Goals

**Goals:**
- Прогон, который идёт через тот же код, что в приложении: планировщик, сборка, проверка, применение. Отличаются только источник фраз, база и часы.
- Метрики, которые можно сравнить между двумя прогонами одного набора без ручной разметки.
- Правки промпта и состояния, которые принимаются только по замеру.

**Non-Goals:**
- Детерминированность агента. Разброс между прогонами меряем, а не устраняем.
- Внутренний экран прогона и ручная разметка.
- Снижение стоимости вызова через кеш.
- Изменения схемы базы.

## Decisions

### 1. `grill-eval` — бинарник внутри крейта

В `src-tauri/Cargo.toml` добавляется `[[bin]] name = "grill-eval"`. Код живёт в новом модуле `src-tauri/src/eval/`, библиотека отдаёт его как `pub mod eval` с одной точкой входа `eval::cli::main(args)`. Модули приложения остаются приватными, наружу ничего больше не выходит. Подкоманды:

- `export <recording-id> [--name N]` — запись из базы приложения в набор;
- `import <аудио> [--others <аудио>] [--channels left=me|right=me|mono] --project <описание.md> [--docs <файлы>] [--people <people.json>] [--name N]` — внешняя запись в набор (решение 2а);
- `brief <набор>` — пересобрать бриф набора нынешним промптом брифа;
- `replay <набор> [--from M --to M] [--label L] [--rules FILE]` — прогон;
- `judge <отчёт>` — разметка;
- `compare <отчёт A> <отчёт B>`.

База приложения открывается только на чтение и только в `export`.

*Альтернативы.* Скрипт на TS вроде `spikes/agent/bench.ts` пришлось бы держать в синхроне с Rust-логикой сборки и проверки, и он мерил бы другой код. Режим `--eval` в бинарнике приложения тянул бы в CLI окна Tauri. `#[ignore]`-тест с переменными окружения неудобен как инструмент: нет подкоманд и отчётов.

### 2. Набор звонка — один JSON-файл

Файл `<имя>.json` в `.grill-eval/corpus/` в корне репозитория; каталог `.grill-eval/` добавляется в `.gitignore`. Содержимое:

- версия формата;
- проект: название, описание, заметки, бриф;
- тексты прочитанных источников (нужны подкоманде `brief`);
- люди и участники записи;
- глоссарий записи;
- запись: время начала и длительность;
- сегменты живого прохода: id, канал, `start_ms`, `end_ms`, текст.

Расшифровка уточнённого прохода, если она есть, кладётся отдельным полем: по ней работает судья. Вопросы и вызовы исходного звонка тоже сохраняются, чтобы сравнить прогон с тем, что было вживую.

### 2а. Импорт внешней записи

1. **Каналы.** `ffmpeg` (на машине разработчика, не в приложении) декодирует вход в 16 кГц моно PCM на каждый канал:
   - два файла: `--others` задаёт дорожку клиента;
   - стерео: каналы делятся по `--channels`;
   - моно: одна дорожка `mixed`.

   Аудио копируется в `.grill-eval/audio/`.
2. **Живой проход.** Каждый канал идёт через тот же VAD-нарезчик, что в записи, и распознаётся живыми заданиями распознавателя с глоссарием записи. Время фразы — её положение в файле. Так набор получает «живую» расшифровку того же качества, какое видел бы быстрый контур. Подавать файл в реальном времени не нужно: нарезка и распознавание от темпа не зависят.
3. **Уточнённый проход.** Те же каналы через путь второго прохода (beam search, полный глоссарий) для судьи.
4. **Моно.** Каналов нет, поэтому после распознавания один вызов Claude Code со схемой размечает каждую фразу как «Я» или «Остальные». Он получает уточнённую расшифровку, описание проекта и имя менеджера, если оно задано. Фразы на границе двух говорящих VAD не делит, и такая фраза целиком уходит одному говорящему. Набор получает `channels: "approximate"`, и отчёт печатает это в заголовке.
5. **Проект.** Описание из `--project`, документы из `--docs` (их текст читает тот же извлекатель, что у источников проекта), люди из `--people`. Бриф набора собирается подкомандой `brief` (задача 3.4).

Распознаватель берётся у приложения: те же модели в каталоге моделей приложения. Если модели не скачаны, импорт завершается ошибкой с подсказкой открыть приложение.

*Альтернатива для моно* — модель диаризации (pyannote и подобные). Это новая тяжёлая зависимость с Python или ONNX ради инструмента разработки. Разметка по тексту дешевле, а пометка «приблизительно» честно отделяет такие наборы при сравнении.

### 3. Прогон: временная база и виртуальные часы

`replay` создаёт базу в памяти (`storage::open_in_memory`), заводит в ней проект, людей, бриф и запись из набора и запускает `FastLoop` с собственным `LoopHost`. Тот пишет события в журнал прогона, а не окнам. Агент берётся из настоящего `claude_cli` с тем же `CallOptions`, что в приложении. Каталог промптов временный.

Часы:

- **tokio.** Рантайм `current_thread` с `tokio::time::pause()`. Драйвер берёт из набора следующую фразу с отметкой `t` (её `end_ms`):
  - если вызова агента нет, драйвер сдвигает часы до `t` (`tokio::time::advance`), вставляет сегмент в базу и зовёт `phrase`;
  - если вызов идёт, драйвер двигает часы шагами по 100 мс вместе с реальным временем. Фразы, чья отметка наступила во время вызова, вставляются по ходу, поэтому видны следующему вызову.

  Простой без вызова пропускается мгновенно. 75-минутный звонок займёт примерно сумму длительностей вызовов: 271 × ~3,5 с ≈ 16 минут.
- **Стенные часы.** В `LoopHost` добавляется `fn now_ms(&self) -> i64`. Приложение отдаёт `storage::now_ms()`, прогон — `started_at + виртуальное время`. Все места в контуре, которые пишут время вызова или вопроса, берут его у хоста. Тогда «минуты с последнего вопроса» (решение 7) одинаково считаются вживую и в прогоне.
- **Флаг `--realtime`.** Вместо виртуальных часов прогон идёт на настоящих. Это проверка на случай, если виртуальные часы где-то расходятся с живым поведением; результат сравниваем на коротком звонке (задача 2.5).

`--from/--to` отбирают сегменты по `start_ms`. Время в отчёте всегда отсчитывается от начала звонка. `--rules FILE` подменяет `RULES` текстом из файла, чтобы сравнивать варианты промпта без пересборки. В отчёт пишется хеш текста правил.

*Альтернатива.* Подавать фразы в настоящем времени. Это честно, но 75 минут на прогон, а на остановленных часах тот же результат получается за долю времени.

### 4. Судья — один вызов на звонок

`judge` вызывает Claude Code (`claude-sonnet-5-5`, effort medium) со схемой ответа. Судья получает:

- всю расшифровку звонка: уточнённую, если есть, иначе живую; с каналами и временем;
- проект и бриф;
- показанные вопросы прогона с временем появления, темой, полем, типом пробела и основанием.

Судья возвращает:

- для каждого вопроса метку (`would_ask`, `off_topic`, `already_answered`, `fabricated`, `duplicate`) и обоснование одним предложением со ссылкой на сегмент, если она есть;
- список вопросов менеджера: id сегмента «Я», где менеджер спросил клиента о задаче, без реплик-связок;
- для каждого вопроса менеджера — id вопроса агента, показанного до этого сегмента и спрашивающего о том же, или `null`.

Ссылки на сегменты и вопросы код проверяет. Метка с несуществующим id отбрасывается, такой вопрос считается неразмеченным. Если звонок не помещается в окно судьи (больше ~150 тыс. символов), расшифровка режется на части по 30 минут с перекрытием 5 минут, а списки вопросов менеджера сливаются по id сегмента.

*Альтернатива.* Сравнивать с вручную составленным списком вопросов опытного менеджера. Это точнее, но списка нет, а вопросы самого менеджера в звонке — честная замена «покрытия». Ручную разметку отложили вместе с экраном.

### 5. Метрики и сравнение

Метрики отчёта:

| Метрика | Как считается |
|---|---|
| Доля полезных | `would_ask` / размеченные |
| Доля выдуманных | `fabricated` / размеченные |
| Покрытие | покрытые вопросы менеджера / все вопросы менеджера |
| Первый вопрос темы | время от создания темы до её первого вопроса |
| Самая длинная пауза | наибольший промежуток между новыми вопросами, в который клиент сказал хотя бы 5 фраз |
| Темы | число тем |
| Отброшенное проверкой | число по причинам и до трёх примеров на причину |
| Вызовы | число, p50/p95 длительности, токены, стоимость |

`compare` выводит таблицу «A | B | разница» и пары вопросов. Пара — вопросы с одной темой, похожие по триграммам (`similarity.rs`, тот же порог 0.6). Вопросы без пары попадают в «появились» и «пропали».

### 6. Пробелы брифа: поле `gaps`

В `Brief` добавляется `gaps: Vec<BriefGap>` с `#[serde(default)]`, у `BriefGap` поля `lens: CardLens` и `text: String`. Старые брифы читаются с пустым списком, `deny_unknown_fields` остаётся.

Изменения в промпте и схеме:

- раздел `gaps`: «чего в материалах нет и что нужно, чтобы оценить или реализовать продукт; до 10 пунктов; не утверждай фактов; линза — одна из семи»;
- схема ограничивает список (`maxItems: 10`), линзу (enum) и длину текста (до 200 символов);
- после сборки код обрезает лишнее.

В префиксе пункты идут отдельным разделом «Неясно до звонка», с ID `G1…Gn` и линзой: `G1 (пользователи): …`. Они становятся `SourceText` с новым видом источника. В `evidence` используется `source: "project"`, а ID `G…` проверяется как пункт проекта.

В `validate.rs` основание `G…` засчитывается для `question`, но не засчитывается фактом для `card` и `answered`, так же как фраза «Я».

Правило в `RULES`: пункт «Неясно до звонка» поднимается вопросом, когда клиент заговорил о его линзе в текущей теме. Основание — пункт `G` и фраза клиента. Пункт, на который уже есть вопрос звонка, не повторяется: это ловит существующая проверка на повторы.

Фронтенд:

- блок брифа (`brief-section.tsx`) показывает раздел «Неясно до звонка» списком с подписью линзы, только когда пункты есть;
- экспорт добавляет тот же раздел;
- моки брифа получают два-три пункта.

### 7. Состояние вызова: нераскрытые линзы и паузы

`assembly::user_message` дополняется двумя вещами:

- **Под карточкой текущей темы:** «Пустые линзы: пользователи, критерии готовности». Список считается кодом по пустым полям.
- **Строка о паузе:**
  - если последний новый вопрос звонка (или начало темы, если вопросов нет) был `N ≥ 5` минут назад, а после него есть фразы «Остальных», состояние пишет: «N мин без новых вопросов. Проверь: нераскрытые или пустые линзы текущей темы, допущения, не перешёл ли клиент к другой задаче»;
  - меньше 5 минут — строки нет;
  - время берётся из `LoopHost::now_ms` (решение 3).

Порог 5 минут — константа. Её подбирает прогон (задача 4.4).

Стабильная часть от этого не меняется: всё это идёт в сообщение, а не в префикс.

### 8. Правила: «не раскрыто» и темы

В `RULES` меняются:

- **Описание `empty`:** «не раскрыто: поле пустое ИЛИ записано общими словами без того, что нужно для оценки (кто именно, сколько, при каком условии, какая система)». Код не меняется: он и сейчас не требует пустого поля для `empty`. В `RULES` и в схеме патча меняется только описание.
- **Правило тем:** «новая тема — когда клиент перешёл к другой задаче, функции или подсистеме (другие пользователи, другой сценарий, другая интеграция), даже если он не сказал „теперь о другом“; small talk и уточнения той же задачи — не тема».
- **Правило первого вопроса темы** остаётся.

Каждая правка правил — отдельный файл варианта для `--rules`, который принимается по сравнению с основным (задача 4).

### 9. Пороги проверки и эмбеддинги

Пороги меняются только при выполнении условий:

- **Совпадение цитаты** (0.75 / 80 %) — если среди `quoteNotFound` прогона больше 20 % ложных: судья или ручной просмотр примеров видит дословную цитату с ошибкой распознавания.
- **Повторы** (0.6) — если пары вопросов, которые судья пометил `duplicate`, прошли проверку.

Если больше 10 % показанных вопросов судья помечает `duplicate`, а триграммы их не ловят, решение об эмбеддингах записывается в `docs/spikes/question-quality.md` отдельной задачей. В этом изменении эмбеддинги не добавляются.

## Risks / Trade-offs

- **[Разброс агента между прогонами]** → короткие звонки гоняем по два раза на вариант. Изменение принимаем, если доля полезных и покрытие не хуже ни в одном из двух прогонов, а пауза и время до первого вопроса стали лучше.
- **[Судья ошибается]** → обоснование и ссылка на сегмент у каждой метки. В отчёте до трёх примеров на метку, чтобы глазами проверить спорные. Судья один и тот же для обоих прогонов сравнения.
- **[Покрытие по вопросам менеджера — не «правильные» вопросы]** → это нижняя оценка. Вопросы агента, которые менеджер не задал, но судья счёл «задал бы», видны в доле полезных.
- **[Стоимость]** → 75-минутный звонок ≈ $10 за прогон. Основной цикл идёт на коротких звонках и отрезке длинного (`--from 40 --to 75`, где вопросы иссякли), а полный длинный прогон делается один раз в конце. Стоимость каждого прогона видна в отчёте.
- **[Виртуальные часы расходятся с живым поведением]** → флаг `--realtime` и сверка на коротком звонке (задача 2.5). Расхождение по числу вызовов больше 10 % — ошибка прогона, а не повод менять контур.
- **[Пробелы брифа превращаются в вопросы «по чек-листу»]** → пункт поднимается только при касании темы и только со ссылкой на фразу клиента. Доля `off_topic` в прогоне — контроль.
- **[Больше тем — больше дробления]** → метрика «темы» и доля `off_topic`. Если тем больше 2 на 10 минут, правило тем ослабляется.
- **[Данные клиентов]** → наборы, аудио и отчёты в `.grill-eval/` под `.gitignore`. Импорт и распознавание локальные. В Claude Code уходит только текст: для разметки моно, сборки брифа, прогона и судьи, то есть то же, что уходит из приложения во время звонка. В `docs/` попадают только цифры и обезличенные примеры.
- **[Моно разделено с ошибками]** → факты в контуре берутся только из «Остальных», так что ошибка разметки меняет поведение агента. Наборы с пометкой «приблизительно» сравниваются только между собой, а выводы по порогам проверки (решение 9) делаются по наборам с настоящими каналами.
- **[Формат записей неизвестен]** → импорт принимает всё, что декодирует `ffmpeg`. Первую запись проверяем вручную: длительность, каналы, выборочно 10 фраз против аудио.

## Migration Plan

- Схема базы не меняется.
- Бриф: старые читаются без пробелов, пробелы появляются после пересборки. Бриф «Обменника» пересобирается в живом прогоне.
- Откат правил — возврат файла `RULES`. Откат пробелов — пустой список: префикс тогда пишет «Неясно до звонка: нет».
