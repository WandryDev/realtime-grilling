# Design

## Context

Сейчас звонок существует только во фронтенде:

- **Сессия.** `src/data/call-session.ts` хранит сессию (`idle` / `live` / `finishing`) с `callId = DEMO_CALL_ID`. Каждое изменение рассылается всем окнам событием `CallSessionChanged`, которое шлёт сам фронтенд (`source` — метка окна). Окно применяет чужие изменения.
- **Старт.** «Начать» в виджете (`call-widget/api.ts`) вызывает `recording_start` с проектом и людьми, но без `call_id`. Строка в `calls` не создаётся: таблица пуста, у всех записей `call_id` равен NULL. К тому же `calls.project_id` объявлен `NOT NULL`.
- **Завершение.** «Завершить» / «Отменить завершение» (`recording/api.ts`) останавливают запись или начинают новую и переключают сессию. «Собираю итоги» идёт в `/call` (`call-page.tsx`), а в конце `post-call/api.ts` вызывает `resetCall()`.
- **Окно без сессии.** `call-page.tsx` при открытии без `live` сессии запускает демо с `DEMO_PROJECT_ID`. Отсюда заголовок «Телемедиа…» у звонка без проекта.
- **Освобождение микрофона.** Его ловят окна (`overlay-page.tsx`, `call-page.tsx`) через `subscribeToMicActivity`, и каждое окно считает свой отсчёт «Завершать звонок сам».
- **Rust.**
  - `mic_watch` сам показывает виджет на «занят» (`show_widget`). Режим `record` трактуется как `widget`.
  - Трей «Начать звонок» и сочетание `toggle-call` всегда показывают виджет.
  - При выходе `recording::stop_on_exit` дописывает файлы. Запись, оставшаяся `recording` после сбоя, при запуске становится `interrupted`.
- **Окна.** Их четыре: `main`, `onboarding`, `widget`, `overlay`. `windows_show(label, route)` показывает окно и шлёт ему `Navigate`.

## Goals / Non-Goals

**Goals:**

- Бэкенд владеет текущим звонком: единственный источник правды, общий для окон, без гонок между ними.
- Звонок всегда в базе, а записи, вопросы и транскрипт к нему привязаны.
- Переходы окон и отсчёт автозавершения работают, даже когда окна скрыты.

**Non-Goals:**

- Содержимое итогов (`calls.summary` остаётся JSON фронтенда) и история на реальных данных — задача «После звонка».
- Изменение внешнего вида экранов. Меняются только источники данных и пустые состояния.

## Decisions

### 1. `CallManager` в Rust — владелец текущего звонка

Новый модуль `src-tauri/src/call/` с состоянием `Idle | Live | Finishing`, под мьютексом в `State`:

- **Последовательность.** Все переходы идут последовательно через один асинхронный замок (`tokio::sync::Mutex`): старт, завершение, отмена, «Продолжить», автозавершение и «Сразу записывать». Так два «Начать» из двух окон дают один звонок.
- **Событие.** После каждого перехода бэкенд шлёт `CallSessionChanged` всем окнам.

Альтернативы:

- Оставить рассылку во фронтенде. Скрытое окно не считает таймер, окна гоняются при старте, а звонка в базе всё равно нет.
- Держать состояние только в базе. Таймер и последовательность всё равно нужны в процессе, а база остаётся местом хранения.

### 2. Команды

| Команда | Что делает |
|---|---|
| `call_current()` | Текущий `CallSession`, для окна, открытого посреди звонка. |
| `call_start({ projectId?, participantIds })` | В `Live` возвращает текущий звонок. Иначе в одной транзакции создаёт `calls` (`live`, `started_at`) и `call_participants`, затем `RecordingManager.start` с `RecordingLinks { call_id, project_id, participant_ids }`. Если запись не началась, строка звонка удаляется: в ней ничего нет, а «идёт» без записи запрещено спекой. Ошибка доступа уходит в окно как сейчас (`noAccess`). |
| `call_finish(callId)` | Из `Live`: остановка записи, `ended_at`, статус `finishing`. В остальных состояниях ничего не делает. |
| `call_resume(callId)` | Из `Finishing`: новая запись того же звонка, статус `live`, `ended_at = NULL`. Если запись не началась, звонок остаётся `live` без записи, а тост объясняет причину, как сейчас. |
| `call_close(callId)` | Итоги собраны: `finished`, текущего звонка нет. |
| `call_keep(callId)` | «Продолжить»: снимает отсчёт до следующего освобождения микрофона. |

Неизвестный `callId` возвращает `NotFound`, а `callId` не текущего звонка — `Invalid`. `calls_create` и `calls_update` остаются для правок данных (название и т. п.). Статус и время звонка меняет только `CallManager`.

### 3. Миграция `0006`: звонок без проекта

`calls.project_id` становится необязательным, `ON DELETE CASCADE` для звонков проекта сохраняется. В SQLite это пересборка таблицы `calls` (копирование, переименование), внутри миграции с `PRAGMA foreign_keys` по правилам rusqlite_migration, как в прошлых миграциях. Проверка — тест миграции с базы версии 5: строки сохранены, `foreign_key_check` пуст.

`Call.project_id` превращается в `Option<String>`, и `bindings.ts` меняется. Адаптер `src/data/calls.ts` показывает звонок без проекта как «Звонок без проекта». `title` в базе остаётся пустым: название вычисляется на экране.

### 4. `CallSessionChanged` шлёт бэкенд

Поле `source` уходит. `CallSession` получает:

- `participantIds` рядом с именами;
- `autoEnd: Option<{ app, releasedAt, endsAt }>` — общий отсчёт, окна только рисуют `endsAt - now`.

Порядок событий: сначала `DataChanged` звонка, затем `CallSessionChanged`. Так окно, получившее сессию, находит звонок в сторе.

### 5. Переходы окон в одном месте

Переходы выполняет `call/windows.rs` по смене состояния, а не окна:

- **`Idle → Live`** (старт): скрыть `widget`. При `compactOverlay` показать `overlay`, иначе `main` с маршрутом `/call`.
- **`Live → Finishing`**, откуда бы ни пришло «Завершить»: окно звонка, оверлей, трей или отсчёт. Скрыть `overlay`, показать `main` с `/call`. Там «Собираю итоги» и «Отменить завершение», как сейчас. Если главное окно уже на `/call`, повторная навигация ничего не меняет.
- **`Finishing → Live`** («Отменить завершение»): окна остаются как есть.
- **`Finishing → Idle`** (`call_close`): окна не трогаются, главное уже открывает итоги.

Фронтенд перестаёт сам вызывать `windows_show` при старте и завершении (`start-widget-page.tsx`, `afterStartHref`). Ручные переходы остаются его: «Развернуть», «Открыть Grill» и т. п.

### 6. Отсчёт автозавершения в бэкенде

У `mic_watch` появляется наблюдатель переходов, на него подписывается `CallManager`. По «освободился» в `Live`:

- если `autoEnd` не «Никогда», записать `autoEnd { app, releasedAt, endsAt = releasedAt + N }` и запустить `tokio::time::sleep_until`;
- по «занят» или `call_keep` снять отсчёт и отменить задачу;
- по истечении выполнить тот же путь, что `call_finish`.

Настройка читается в момент освобождения. Изменение настройки во время отсчёта на него не влияет, что проще и предсказуемо. Окна перестают слушать микрофон ради отсчёта и рисуют `session.autoEnd`.

### 7. «Сразу записывать» и последний звонок

`mic_watch` на «занят» с поведением `record`, без текущего звонка и без пометки «в этот период уже завершали» вызывает `CallManager.start` с настройкой последнего звонка:

- последний звонок — `calls` по `started_at DESC`;
- берётся его проект, если он ещё существует, и те участники, которые ещё существуют;
- без звонков звонок идёт без проекта.

Показывается оверлей, независимо от `compactOverlay`: «сразу» значит без окна, закрывающего звонилку. Пометка ставится, когда звонок этого периода переходит в `Finishing`, и снимается на «освободился».

Виджет предзаполняется по тому же правилу на фронтенде, из стора звонков (`resolveProjectId` и выбор людей). Отдельная команда не нужна.

### 8. Трей и сочетание

`tray.rs` пересобирает меню по смене состояния:

- в `Live` и `Finishing` — «Открыть звонок» и «Завершить звонок» вместо «Начать звонок»;
- «Открыть звонок» — то же, что `toggle-call` во время звонка;
- «Завершить звонок» вызывает `call_finish`.

`toggle-call` в звонке показывает оверлей при `compactOverlay`, иначе `main` с `/call`. Без звонка он показывает виджет, как раньше.

### 9. Восстановление и выход

Один путь для сбоя и выхода. При запуске, после открытия базы и пометки прерванных записей, `calls::finish_stale(now)` переводит `live` и `finishing` в `finished`:

- `ended_at` — максимум `ended_at` его записей;
- если записей нет, `ended_at = started_at`.

При выходе `stop_on_exit` уже останавливает запись. Звонок закрывается при следующем запуске тем же `finish_stale`, так что выход не ждёт базу дольше нынешнего.

### 10. Фронтенд

**Сессия.** `src/data/services/call-session.ts` становится сервисом `CallSessionBackend`:

| | `layerTauri` | `layerMock` |
|---|---|---|
| Чтение | `call_current` и `listen(events.callSessionChanged)` | нынешняя логика стора внутри страницы, `DEMO_CALL_ID` |
| Действия | `start` / `finish` / `resume` / `close` / `keep` — команды из решения 2 | то же, в памяти страницы |

`call-session.ts` хранит то, что пришло от бэкенда. Действия вызывают сервис и не рассылают ничего. `adoptRunningRecording` и `attachRecording` уходят: запись звонка знает бэкенд.

**Экраны.**

- `call-page.tsx` и `overlay-page.tsx` берут проект, участников, время и отсчёт из сессии.
- В Tauri без звонка окно звонка показывает пустое состояние «Звонка нет» с «Начать звонок» (виджет) и не запускает демо. В браузере демо остаётся.
- Заголовок — имя проекта или «Звонок без проекта».

**Итоги.** `post-call/api.ts` в конце сборки вызывает `close` вместо `resetCall()`. Маршрут итогов получает настоящий `callId`.

**Удаление данных.** «Удалить все данные» (`privacy-section.tsx`) во время звонка сначала завершает звонок.

## Risks / Trade-offs

- [Главное окно скрыто и не загружено, когда приходит `Navigate`] → `windows_show` уже показывает окно и шлёт маршрут. Окно при загрузке читает `call_current` и в `Finishing` само встаёт на `/call`.
- [Итоги собирает фронтенд главного окна: перезагрузка посреди сборки] → `call-page` в `Finishing` начинает сборку заново. Звонок не застрянет: при следующем запуске его закроет `finish_stale`.
- [Пересборка `calls` в миграции] → в реальных базах таблица пуста. Тест миграции проверяет копирование и внешние ключи, а копия базы до миграции уже сохраняется.
- [Отсчёт идёт по часам бэкенда, окна рисуют по своим] → окна считают от `endsAt` по `Date.now()`. Расхождение — доли секунды, на одной машине.
- [«Сразу записывать» начнёт звонок на любой захват микрофона: диктовка, голосовые сообщения] → так и задумано настройкой. Звонок можно завершить, и в тот же период занятости он не начнётся снова.
- [Изменение контракта `CallSessionChanged`] → событие внутреннее, окна обновляются вместе с бэкендом. Сброс `bindings.ts` проверяет CI.

## Migration Plan

Миграция `0006` применяется при первом запуске новой версии, копия базы до неё сохраняется, как в `0005`. Отката схемы нет: прежняя версия не открывает базу версии 6, так что откат — восстановление копии.
