# Концепт: ассистент для грилинга клиента во время звонка

> Статус: концепт согласован (2026-10-19). Детали UI прорабатываются в Paper.
> Референс: [Granola](https://www.granola.ai/) — real-time транскрибация без бота в звонке.

## Что это

Десктоп-приложение (**Tauri, macOS + Windows сразу**). Пока менеджер разговаривает с клиентом, приложение в реальном времени транскрибирует звонок и **автоматически** подсовывает менеджеру вопросы, которые стоит задать. Менеджер ничего не печатает и не нажимает во время разговора — только читает и решает, задавать ли вопрос.

**Сценарий:** discovery по задачам внутри текущих проектов (от мелких до крупных, например «система приёма звонков»), также подходит для обсуждения проекта целиком.

## Звонок от начала до конца

1. **Старт.** При активации микрофона появляется виджет с предзаполненными последним проектом и участниками (меняются одним кликом) → менеджер жмёт «Начать».
2. **Во время звонка.** Компактное окно поверх всех окон, скрытое от screen share.
   - В фокусе — вопросы по **текущей теме**, рядом счётчик незакрытых по прошлым темам.
   - Список стабильный: новые вопросы мягко подсвечиваются, отвеченные уходят сами.
   - Агент сам разбивает разговор на темы/задачи.
   - Когда разговор идёт к завершению — автоматически включается **финальная проверка**: самые важные незакрытые вопросы по всем темам.
3. **Конец.** Когда микрофон перестаёт использоваться (не mute, а именно никто, кроме нас, его не использует) — предложение завершить звонок. Если менеджер не отреагировал за N минут (настройка, 5–10 мин) — звонок завершается автоматически.
4. **После звонка.** Summary, TL;DR, незакрытые вопросы и **предложенные обновления** брифа проекта и профилей клиентов. Ничего не применяется без подтверждения менеджера. Итог хранится только в приложении.

## Мозг

- **Агент — локальный CLI пользователя** (первым — Claude Code) за интерфейсом «Агент», чтобы можно было заменить на другой CLI или прямой API. Окончательное решение — после замера задержки. Лимиты подписок решаются на уровне руководства.
- **Быстрый контур.** Триггер — пауза в речи клиента, но не чаще ~20 с. Без инструментов, только с уже загруженным контекстом. Агент возвращает **патчи** (а не полный список заново); конкретный набор операций — позже.
  - **Состояние хранит приложение, каждый вызов агента независим** (вместо одной долгой сессии на звонок). Источник правды — SQLite, а не память агента: в долгой сессии контекст растёт, задержка растёт вместе с ним, а сжатие истории внутри CLI неконтролируемо.
  - Сборка каждого вызова: стабильная часть (системный промпт + бриф + профили людей, кешируется) → текущее состояние (карточки, открытые вопросы с ID) → последние N минут транскрипта.
  - Это же упрощает выбор «CLI или прямой API»: через API проще получить строгий структурированный вывод и контролировать кеш.
- **Медленный контур.** В фоне ищет в Outline / GitHub / ClickUp то, что всплыло в разговоре, и подмешивает найденное в контекст быстрого контура. Не блокирует быстрый контур.
- **Источник вопросов.** Агент ведёт живую «карточку задачи» и смотрит на неё через универсальные линзы (цель, пользователи, сценарии, крайние случаи, интеграции, ограничения, критерии готовности). Вопросы рождаются там, где пусто, допущение или противоречие. Плейбук пользователь не пишет.
- **Профиль клиента** влияет только на **формулировку** вопросов (простым языком для нетехнического клиента, по существу — для технического). Тактические подсказки в MVP не делаем.

## Качество вопросов

Цель — точность показанного важнее полноты: если половина списка шум, менеджер перестанет его читать.

**Откуда берутся плохие вопросы:** агент выдумывает факты, которых никто не произносил; задаёт общие вопросы по чек-листу, не связанные с разговором; повторяет то, на что уже ответили или что есть в брифе; цепляется за ошибку распознавания; принимает слова менеджера за факты от клиента.

**Механизмы (по убыванию эффекта):**

1. **Обязательная ссылка на основание, проверяемая кодом.** В каждом `add_question` агент указывает `evidence` (ID сегментов транскрипта / пунктов брифа + короткая цитата), `card_field` (какое поле карточки) и `gap_type` (пусто / допущение / противоречие). Код проверяет, что ID существуют, а цитата нечётко совпадает с текстом; иначе вопрос отбрасывается. Детерминированный фильтр галлюцинаций, дешевле LLM-критика.
2. **Сначала карточка, потом вопросы.** В одном вызове агент сначала обновляет поля карточки (с источниками), затем формулирует вопросы по пробелам. Вопрос, не привязанный к полю карточки текущей темы, отсекается как уход от темы.
3. **Молчание — нормальный ответ.** Пустой патч явно разрешён. Лимиты: не больше 1–2 новых вопросов за вызов, не больше ~5 видимых. Поле `priority` с критерием «блокирует ли это оценку или реализацию».
4. **Дедупликация и «отвечено».** Агенту передаются открытые вопросы с ID; новый вопрос дополнительно сверяется в коде по эмбеддингам с открытыми и отвеченными. `mark_answered` тоже требует цитату.
5. **Агент знает, что текст из ASR.** В промпте: в тексте есть ошибки распознавания, одно странное слово — не повод для вопроса. Факты о задаче берутся только из канала «Остальные».

LLM-критик второй моделью в быстрый контур не ставим (+2–5 с на вопрос); хватает проверки ссылок в коде.

**Режим прогона записанных звонков** — главный инструмент качества. Записанный транскрипт подаётся в контур в темпе реального времени, вопросы размечаются: «задал бы» / не по теме / уже отвечено / выдумано. Метрики: доля полезных среди показанных, доля выдуманных (→ 0), покрытие относительно списка вопросов опытного менеджера. Каждое изменение промпта или модели проверяется прогоном; для масштаба — LLM-судья. Бонусом тот же режим позволяет дорабатывать UI без живых звонков.

## Контекст проекта

- **Онбординг проекта** (один раз): подключаем источники, менеджер добавляет свои заметки и **людей со стороны клиента с профилями** (темперамент, характер, тех. уровень, роль в бизнесе, понимание проекта).
- **Бриф проекта** собирается агентом при онбординге и освежается перед звонком, если устарел. Быстрый контур получает бриф, а не сырые доки.
- **Интеграции (все опциональные; ядро работает без них):**
  - **Outline** — документация (MCP).
  - **GitHub** — код через GitHub MCP. Авторизация — OAuth Device Flow прямо из приложения (один OAuth App организации). Ни git, ни gh не нужны.
  - **ClickUp** — только чтение (MCP). Перед звонком агент по смыслу находит в задачах и комментариях вопросы, которые требуют ответа клиента, и подмешивает их в поток как «входящие из ClickUp» со ссылкой на задачу.
- **Онбординг окружения:** приложение проверяет, установлен ли агент и выполнен ли вход, подключены ли MCP и интеграции, и ведёт по шагам без терминала.
- Токены хранятся в Keychain (macOS) / Credential Manager (Windows), у каждого менеджера свой доступ.

## Звук и транскрипция

- Два канала: **микрофон («Я»)** и **системный звук («Остальные»)**. Бот в звонок не подключается, работает с любой звонилкой. Диаризации внутри канала «Остальные» нет.
- **Локальный STT** для русского и украинского. Есть минимальные требования к железу.
- Аудио хранится локально в Opus (~15–20 МБ на час звонка, два канала). Выгрузка в облако — на будущее, интерфейс хранилища закладываем сразу.

**Распознаём фразами, а не пословным стримингом.** Агент обновляется не чаще ~20 с и по паузе, поэтому VAD режет аудио на фразы (2–15 с), и каждая распознаётся целиком после паузы. Можно взять большую точную модель, у неё есть контекст фразы, задержка 1–3 с после фразы некритична. Пословные частичные результаты нужны только для живой ленты в UI — если она не ключевая, качеством ради неё не жертвуем.

**Где теряется качество (по убыванию):**

1. **Захват звука.** Без наушников голос клиента попадает в микрофон и пишется как «Я». Нужно эхоподавление с системным каналом как опорным сигналом (macOS VoiceProcessingIO, WebRTC AEC3).
2. **Галлюцинации Whisper на тишине** («Продолжение следует…», «Субтитры сделал DimaTorzok»). Silero VAD *перед* моделью, `condition_on_previous_text` выключен, фильтр по `no_speech_prob` / `avg_logprob`, стоп-лист фантомных фраз.
3. **Термины и имена.** Глоссарий из брифа и профилей людей → `initial_prompt` Whisper (≤ ~224 токенов; при перегрузе модель начинает вставлять текст промпта в транскрипт).
4. **Отрицания и числа** («не нужно» ↔ «нужно», «50» ↔ «15») — опаснее десятка опечаток, от них зависят вопросы и summary.

**Модели-кандидаты:**

- **GigaAM** — на русском, вероятно, точнее и быстрее Whisper, но только русский и без подсказки глоссарием.
- **Whisper large-v3-turbo** — русский + украинский, суржик и англицизмы, глоссарий через промпт. На Apple Silicon (whisper.cpp / MLX) ок; риск — Windows без нормальной видеокарты.
- Возможна маршрутизация по языку проекта (ru → GigaAM, uk/смешанный → Whisper) ценой поддержки двух моделей.

**Два прохода:**

- **Реальное время** — точность «достаточная для вопросов». На слабом железе допустима модель поменьше.
- **После звонка** — весь файл перераспознаётся локально тяжёлой моделью с beam search и полным глоссарием. Ограничения по времени нет (20 мин в фоне на час аудио — нормально), поэтому работает даже на слабом железе. Summary и предложения по брифу строятся по этой версии.

**Облачный STT** — не основной путь (по NDA допустим, но это оплата за каждый час). Ориентир цен на 2026: ~$0.18–0.75 за час аудио; при 10 менеджерах × 3 ч/день ≈ 660 ч/мес ≈ $120–250/мес. Платим только за речь, не ×2 за каналы, т.к. шлём фразы после VAD, а не держим поток. Используется только как запасной вариант для реального времени на машинах, не прошедших бенчмарк при онбординге (приложение прогоняет тестовый фрагмент и меряет, тянет ли модель реальное время). Интерфейс STT закладываем сразу, облачную реализацию пишем, только если данные о железе это потребуют.

**Выбор модели — по данным, а не вслепую.** Набор из 5–10 реальных звонков с вычитанными вручную транскриптами; кандидаты прогоняются на целевом железе. Метрики: WER плюс отдельно точность имён, терминов, чисел и отрицаний.

## Данные

Локальный SQLite:

```
Проект → Люди клиента
       → Звонок → Темы/Карточки задач → Вопросы (открыт / отвечен / отклонён)
                → Транскрипт по каналам
```

UUID и метки времени — задел под будущий бэкенд и синхронизацию. Аккаунтов и команд пока нет, один пользователь.

## Сознательно отложено

- UI, поля карточки задачи и вид вопроса на экране — прорабатываются в Paper; модель данных подстроим.
- Конкретные операции патчей от агента.
- Выгрузка аудио в облако.
- Запись итогов в Outline / ClickUp.
- Бэкенд и общие токены организации.
- Автостарт по календарю, автоопределение проекта.
- Тактические подсказки менеджеру.
- Реализация облачного STT (интерфейс закладываем, реализацию — только если бенчмарк железа потребует).

## Технические риски — проверяем первым прототипом

> Итоги замеров и решения по каждому пункту: [`docs/spikes/`](spikes/README.md).

1. **Захват системного звука и детект «микрофон занят кем-то кроме нас»** на обеих ОС: macOS — Core Audio taps / ScreenCaptureKit и process objects (macOS 14+); Windows — WASAPI loopback и перечисление аудиосессий. Плюс эхоподавление при работе без наушников.
2. **Задержка и качество локального STT** на русском/украинском на целевом железе, особенно на Windows.
3. **Задержка вызова агента:** укладываемся ли в ~20 с на обновление при независимых вызовах с кешируемым префиксом и сколько это стоит по лимитам.

## Открытые вопросы / ждём данных

- **Железо менеджеров на Windows** (CPU, GPU, RAM) — определяет, тянет ли локальная модель реальное время и нужен ли облачный запасной вариант.
- **Записи 5–10 реальных звонков** (с согласия) — для бенчмарка STT и режима прогона вопросов.
