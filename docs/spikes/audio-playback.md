# Спайк: воспроизведение записей в WKWebView (Ogg Opus через `grill-audio`)

Задача 1.1 изменения `post-call`, решение 9 в `design.md`. Дата: 2026-11-05.
Машина: MacBook Air M3, macOS 26.6.2, WebKit 21624.5.1.11.3 (`CFBundleVersion` из `WebKit.framework`). Tauri 2.12.5, wry 0.57.1 (`src-tauri/Cargo.lock`).

## Вердикт: «WAV»

Ogg Opus **играет**, но WebKit неверно считает его длительность, а перемотка идёт по времени, которое с реальным звуком не совпадает. Для плеера, который сверяет позицию с репликами и держит два канала вместе (допуск 150 мс), этого мало. Берём запасной вариант: `grill-audio://localhost/<id>/<me|others>?format=wav`, Rust декодирует в WAV (16 кГц, 16 бит, моно). Контроль (WAV) показал точную длительность и нормальную перемотку.

Если захочется всё же отдавать Ogg как есть, нужно проверить в подписанном бандле, что длительность берётся из БД, а перемотка попадает в нужный звук (на слух, по известной реплике). Пока основание для Ogg не набрано.

## Как мерили

- Харнесс на Swift в `/tmp/audio-spike/` (в репозиторий не входит): `WKWebView` + `WKURLSchemeHandler` для схемы `grill-audio`, `mediaTypesRequiringUserActionForPlayback = []`. Страница тоже отдаётся через схему, поэтому запросы к звуку same-origin.
- Файлы: настоящие записи из `~/Library/Application Support/com.dev-wandry.realtime-grilling/recordings/01a1a726-…/` (`me.opus` 590 051 байт, `others.opus` 405 337 байт); оригиналы не трогали, копии в `/tmp`. `ffprobe`/`file`: Ogg, Opus, моно, 16000 Hz (Input Sample Rate), 48 кГц внутри, ~15 кбит/с, **314,68 с** у обоих; гранула последней страницы (EOS) тоже 314,6765 с, то есть файлы корректны.
- Контроль: первые 60 с `me.opus`, `ffmpeg -ar 16000 -ac 1` в WAV (1 920 078 байт), отдаётся тем же обработчиком как `audio/wav`.
- Обработчик отвечает 206 с `Content-Range`, `Accept-Ranges: bytes`, `Content-Length`, `Content-Type: audio/ogg`; без `Range` отдаёт 200.

```swift
if let r = range, r.hasPrefix("bytes=") {            // bytes=S-E
  ...; status = 206; body = data.subdata(in: s..<(e + 1))
  h["Content-Range"] = "bytes \(s)-\(e)/\(total)"
}
h["Content-Length"] = String(body.count)
t.didReceive(HTTPURLResponse(url: url, statusCode: status, httpVersion: "HTTP/1.1", headerFields: h)!)
t.didReceive(body); t.didFinish()
```

**Расхождение длительности.** WebKit показывает 366 и 431 с вместо 314,68, причём у двух файлов одной длины разное значение: оценка идёт по размеру файла и битрейту, а не по грануле последней страницы. Дополнительная проверка: старт с 310 с, 15 с игры, `ended` не пришло, `currentTime` дошёл до 324,5 (файл кончается на 314,68). Длительность не пересчитывается и после воспроизведения.

## Наблюдавшиеся `Range`-запросы

Ogg (`me`): сначала зонды `bytes=0-1`, `0-7`, затем `0-65535`; хвост файла `bytes=589923-589925`; потом блоками по 64 КиБ подряд (`295038-360573` и т. д.); после перемотки новый блок с нового места. WAV: зонды `0-1`, `0-7`, `0-8191`, мелкие чтения заголовка (`0-47`, `12-19`, `20-35`, …), чтение хвоста, дальше блоки ~64 000 байт. Все ответы 206 прошли без ошибок. Всего ~34 запроса на прогон.

## wry 0.57.1: что делает со 206

`wkwebview/class/url_scheme_handler.rs`: запрос превращается в `http::Request` со всеми заголовками (`Range` доходит до обработчика), ответ собирается в `NSHTTPURLResponse` с **кодом статуса из ответа** и всеми его заголовками (`Content-Range`, `Accept-Ranges`), `Content-Length` ставится по длине тела, затем `didReceiveResponse` → `didReceiveData` (всё тело одним куском) → `didFinish`. Срез тела в 206 проходит корректно. Отличия от харнесса: ответ асинхронный, и если вебвью закрылось или задача отменена (WebKit отменяет зонды при перемотке), wry молча отбрасывает ответ (`CustomProtocolTaskInvalid`); стриминга частями нет, тело целиком в памяти, поэтому Rust должен отдавать именно запрошенный срез, а не файл целиком. На Windows схема другая (`http://grill-audio.localhost/`), там WebView2.
